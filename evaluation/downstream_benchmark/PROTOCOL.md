# ErrPilot Downstream Repair Benchmark Protocol

Status: frozen benchmark protocol; no benchmark run has been executed. The
human-approved operational decisions are frozen in `RUN_SPEC_V1.md`.

Protocol ID: `EP-DBP-1`. The controlling run specification is `EP-DBRS-1`.

## Research Question and Scope

The benchmark asks one question: does an ErrPilot-generated structured failure
handoff improve downstream automated repair compared with giving the same
coding agent the raw output from the same captured failure?

This is a Python-centric CLI/pytest debugging benchmark using real BugsInPy
bugs. It evaluates a downstream Codex repair agent. It does not evaluate
ErrPilot as an autonomous repair system, change ErrPilot's architecture, add a
new language or CI/supply-chain domain, or compare multiple models.

## Units and Sample Sizes

- A case is one eligible BugsInPy bug instance at a pinned buggy revision, with
  its official fixed revision and one preregistered bug-exposing oracle.
- The final benchmark contains exactly 24 eligible cases from at least 6 source
  projects, with at most 4 final cases from any one project.
- The main experiment has one paired RAW/ERRPILOT run per final case.
- A robustness subset of 6 randomly selected final cases has two additional
  repetitions per condition. Each robustness case therefore has three total
  runs per condition, including its main run.
- The pilot uses 4 cases labeled `pilot`. Pilot cases do not count toward the
  24 final cases and are permanently excluded from the final eligible pool and
  final sample, whether or not the harness or protocol changes. Pilot outcomes
  must not influence final case selection. A pilot case may never be promoted
  into the final benchmark.

## Paired Conditions

Every paired run uses the same task instruction, pinned case, downstream agent
(Codex), model/configuration, permissions, timeout, and verification oracle.
Each condition starts from its own fresh copy of the identical buggy repository
state.

### A. RAW

The Codex input consists only of:

1. the common task instruction;
2. the exact failing command; and
3. the captured stdout and stderr, byte-for-byte unaltered and clearly
   delimited without diagnosis, summarization, source context, or ErrPilot
   metadata.

The immutable stdout and stderr files are the authority for the prompt payload.
If either stream cannot be represented without alteration by the Codex
invocation interface, the run must stop and record a protocol error rather than
silently normalize it.

### B. ERRPILOT

The Codex input consists only of:

1. the same common task instruction used for RAW; and
2. the Codex handoff artifact generated by the frozen ErrPilot version from the
   case failure evidence.

No extra diagnosis, hand-edited context, or RAW-only material may be appended.
The generated handoff artifact and its producing ErrPilot revision/configuration
must be preserved verbatim.

The exact task-instruction bytes, wrapper constraints, and digest are frozen in
`RUN_SPEC_V1.md`. They must not reveal the official patch or condition label.

## Eligibility and Exclusion

A candidate is eligible only when all of the following are demonstrated from a
reproducible environment:

- the pinned buggy revision reproducibly fails the preregistered oracle;
- the official fixed revision passes the same oracle;
- the observed failure is within current ErrPilot Python CLI/pytest scope;
- no GUI interaction is required;
- the repair does not require test modification; and
- the environment can be reproduced reliably.

Eligibility evidence must include the exact revisions and commands, exit codes,
environment identifier, and hashes or paths for the captured outputs. A
candidate that fails any rule is ineligible. Record it in `exclusions.csv` with
one or more explicit reason codes and supporting evidence; never silently drop
it. Recommended stable reason codes are:

- `buggy_revision_does_not_fail`
- `fixed_revision_does_not_pass`
- `outside_errpilot_scope`
- `gui_required`
- `test_modification_required`
- `environment_not_reproducible`
- `duplicate_bug_instance`
- `eligibility_evidence_incomplete`

Eligible but unselected candidates remain in `cases_manifest.csv` as
`eligible_not_selected`; they are not eligibility exclusions.

Manifest `sample_role` values are `candidate`, `pilot`, `final_main`, and
`final_main_and_robustness`. `exclusion_reason` is blank unless the candidate is
ineligible; an ineligible row must also have a corresponding exclusions-ledger
entry. Final and robustness rows carry sample seed `20260922`.

## Frozen Sampling and Scheduling Rule

The final-case sampling seed is `20260922`.

Before selection, freeze a canonical UTF-8 snapshot of all eligible, non-pilot
candidates and its SHA-256 digest. Candidate keys are
`source_project`, `bugsinpy_bug_id`, and `case_id`. Reject duplicate keys. For
each candidate, compute the lowercase hexadecimal SHA-256 digest of this exact
UTF-8 string:

```text
20260922|final|<source_project>|<bugsinpy_bug_id>|<case_id>
```

Sort by digest and then by the three candidate-key fields. Traverse that order,
accepting a case unless its project already has 4 accepted cases, until 24 are
accepted. Fail closed if 24 cases cannot be selected. The 4-case project cap
implies at least 6 projects in a 24-case final set; verify both constraints
explicitly.

For the robustness subset, compute SHA-256 of
`20260922|robustness|<case_id>` for each of the 24 selected cases, sort by digest
then `case_id`, and select the first 6.

Within every pair and repetition, derive condition order from the low bit of
the first byte of SHA-256 of
`20260922|order|<case_id>|<repetition_index>`. Bit 0 schedules RAW first; bit 1
schedules ERRPILOT first. This scheduling rule affects order only: the two
conditions still use independent fresh states and receive no information from
one another.

## Primary Outcome

The primary outcome is objective repair success on the preregistered
bug-exposing oracle. A condition run succeeds only if:

- the downstream run completes within its frozen timeout;
- the oracle command exits successfully in the resulting workspace;
- no protected test file changed relative to the fresh buggy baseline; and
- no protocol violation occurred.

The oracle is identical across conditions. Tests must not be modified. A test
mutation makes the run unsuccessful and must be reported separately as a
protocol violation; it must not be hidden by resetting before evidence capture.
Other tests may be run for diagnostics, but they do not replace the
preregistered oracle or the primary outcome.

## Secondary Outcomes

For each condition run, record when reliably measurable:

- total Codex token consumption, with input, output, cached/reasoning
  components when the invocation API reports them; and
- `test_invocations_total`, `oracle_invocations_total`, and
  `post_edit_failed_oracle_count` when reliably observable from the frozen
  Codex execution trace.

Token totals must come from authoritative invocation usage metadata and include
all Codex activity inside the condition boundary. Instrumentation definitions
and the `NA` policy are frozen in `RUN_SPEC_V1.md`. If the interface cannot
expose a quantity reliably, store `NA` plus a measurement-status reason; do not
estimate from text length or report an unobservable value as zero.

## Contamination Controls

- Build RAW evidence and the ErrPilot handoff before downstream repair runs;
  preserve and hash both inputs.
- Use separate fresh workspaces created from the same pinned buggy revision for
  every condition and repetition. Never reuse or reset an agent-mutated
  workspace for its pair.
- Do not expose the official fixed patch, fixed worktree, paired-condition
  output, prior repetitions, outcome labels, or oracle result to Codex except
  for feedback explicitly allowed by the one frozen agent configuration.
- Do not share conversation/session state, caches containing prior solutions,
  writable directories, or generated repair artifacts across runs.
- Keep the agent identity, model/configuration, permissions, timeout, task
  instruction, and oracle fixed across RAW and ERRPILOT.
- Execute the oracle in a separate verifier boundary after preserving the agent
  output and workspace diff.
- Detect and report all baseline changes, especially protected test changes,
  before cleanup.
- Record condition order and timestamps so infrastructure drift can be audited.

## Reproducibility and Evidence

Each case must pin source and fixed revisions, failing and oracle commands, the
reproducible environment, protected test paths, and eligibility evidence. Each
run must preserve configuration, prompt/input bytes, stdout, stderr, exit
status, timing, workspace diff, file hashes, oracle evidence, mutation check,
usage metadata, test/oracle invocation instrumentation evidence, and result
record. Raw artifacts are immutable; derived summaries refer to them by digest.

The runner must refuse execution if the worktree/revision, environment,
instruction, Codex identity/configuration, permission profile, timeout,
ErrPilot revision/configuration, oracle, or protected-test manifest differs
from the frozen run specification.

## Pre-Run Gates

The exact common task text, downstream client/model/reasoning identity,
permission profile, timeout, eligibility repetition threshold, protected-test
manifest requirements, instrumentation, `NA` policy, pilot policy, and failure
taxonomy are frozen in `RUN_SPEC_V1.md`. Per-case revisions, immutable
environment and dependency identities, protected paths, oracle identities, and
the remaining evidence listed by that specification must still be completed
and frozen before execution. No runner may choose defaults silently. This
protocol and its run specification do not authorize a pilot or repair run.
